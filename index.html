How to use this guide

Each domain tab below is a self-contained study path — what to learn, what resources cover it, what to build, and how to check yourself.

1 Pick a domain tab

The 5 domain tabs are ordered the way you should study them — Domain 1 first because it's 27% of the exam, then Domain 2, etc. Each tab contains everything you need for that domain in one place: Topics → Resources → Labs → Self-check. No more cross-referencing.

2 Work through it

Read or watch the resources, tick off topics as you understand them, build the lab, then answer the self-check questions out loud or in writing. If you can't answer cleanly, revisit the resources for that domain.

3 Use the Schedule tab as a day-by-day rhythm

The Schedule tab tells you which domain to focus on each day for 30 days. Each day's checkbox links back to the relevant domain.

4 Take mocks in the final week

Days 25 and 28 are full 60-question mock exams. The Exam Day tab covers logistics for the real thing.

Exam reality check: wrong answers are designed to sound like good engineering. The exam tests judgment, not recall. That's why every domain tab below has a Labs section — you need to build these things, not just read about them.

Quick exam facts

60 scenario-based multiple-choice questions, anchored to 6 production scenarios (4 randomly served per sitting): customer support agent, code generation, research system, developer productivity, CI/CD pipeline, data extraction. 120 minutes total, 720/1000 to pass. Credential valid 2 years. $99 USD, free for Anthropic Partner Network members.

Domain 1 — Agentic Architecture & Orchestration

How Claude operates inside autonomous agent loops. The biggest domain — start here.
27% of exam

1 Topics to master

Tick each one as you understand it. Aim to be able to explain each in your own words.

Observe → Think → Act → Respond loop. What happens in each phase, what data flows between them, where things commonly break.
The 5 agentic patterns: prompt chaining, routing, parallelization, orchestrator-workers, evaluator-optimizer. When to use each.
Workflows vs. agents. The trade-off: predictability vs. flexibility. When a simple workflow beats an autonomous agent.
Subagent orchestration: parallel vs. sequential dispatch, how the parent passes context to children, how results are aggregated.
Minimal-footprint design. Smallest possible agent that solves the problem — fewer tools, fewer turns, fewer subagents = more reliable.
Clarifying ambiguity before kicking off a long autonomous run. When to ask the user vs. when to assume.
Human-in-the-loop interrupt design. Where to insert checkpoints, how to surface decision points cleanly.
Failure recovery: what to do when a subagent times out, returns garbage, or contradicts another subagent's output.

3 Hands-on labs

Lab 1A — Build a tool-using agent
~2 hours • Maps to scenarios: Research, Dev Productivity
  1. Install claude-agent-sdk. Build an agent with 3 tools: search_web, calculator, save_note.
  2. Task it with: "Research the top 3 EV manufacturers by 2025 deliveries, calculate market share, save a markdown summary."
  3. Log every observe→think→act step. Watch the loop.
  4. Deliberately break one tool. Observe the failure. Add a recovery path.
Lab 1B — Orchestrator-worker pattern
~2 hours • Maps to scenarios: Research, Customer Support
  1. Build a parent agent that decomposes a question into 2–3 parallel research subtasks.
  2. Dispatch each to a worker subagent. Wait for all to return.
  3. Synthesize results in the parent.
  4. Add a timeout + fallback path for when a worker fails.
  5. Add a human-in-the-loop checkpoint before the final synthesis step.

4 Self-check (answer out loud before moving on)

Q1You're building a code-review agent. Should it be a single autonomous agent with file-edit tools, or an orchestrator dispatching review-specific subagents? What governs the choice?
Q2A subagent returns an answer that contradicts another subagent. The parent has to decide. Name 3 strategies and when each is appropriate.
Q3Why is "minimal-footprint" agent design more reliable than feature-rich? Give a concrete example.
Q4When should an agent ask the user a clarifying question vs. just proceed with an assumption?

Domain 2 — Claude Code Configuration & Workflows

Configuring Claude Code correctly for production projects.
20% of exam

1 Topics to master

CLAUDE.md structure: what goes in it, what doesn't, how it gets injected into context.
Settings hierarchy: user (~/.claude/settings.json) → project (.claude/settings.json) → local (.claude/settings.local.json). Which overrides which.
Slash commands: how to define them in .claude/commands/, scoping rules, argument passing.
Hooks: PreToolUse, PostToolUse, UserPromptSubmit, Notification — when each fires, how to block actions.
Permissions: allowed/denied tool patterns, MCP server allow-lists, how permission prompts work.
Subagents in .claude/agents/: the agent definition file, when Claude Code invokes them automatically.
MCP server config inside .claude/settings.json — adding, scoping, and debugging servers.

Domain 3 — Prompt Engineering & Structured Output

The tricky one — wrong answers sound like good engineering.
20% of exam

1 Topics to master

XML tagging and role separation. Why XML > markdown for structuring complex prompts.
System vs. user vs. assistant message roles, and what belongs in each.
Chain-of-thought — when to use it, when it hurts, how extended thinking differs.
Prompt chaining: breaking a complex task into sequential prompts where each builds on the last.
Few-shot examples: how many, how to pick them, how they bias output.
Prefilling assistant turn with { or other tokens to force structure.
JSON / structured output: when to use a schema, when prefilling is enough, when tool-use is the right mechanism.
Common failure modes: over-specification, contradicting instructions, instructions that the model can't follow.

Cover-to-cover read. Especially: "Use XML tags," "Chain prompts," "Prefill response," and "Be clear and direct."
 OfficialPrompt Engineering Interactive Tutorial — GitHub
Free Jupyter notebooks. The single fastest way to internalize Domain 3. Run every cell.

JSON mode, tool-use as structured output, prefilling strategies.

3 Hands-on labs

Lab 3A — Production-grade classification prompt
~2 hours • Maps to scenarios: Customer Support, Data Extraction
  1. Write a single prompt that takes a customer message and returns JSON with sentiment, topic, urgency.
  2. Use XML tags, 3–5 few-shot examples, and JSON prefilling.
  3. Build a 20-example test set by hand. Include 5 ambiguous edge cases.
  4. Run the prompt across all 20, compute accuracy. Iterate until 90%+.
  5. Compare with and without chain-of-thought enabled — note the trade-off.
Lab 3B — Prompt chain
~1.5 hours
  1. Break a complex task into 3 sequential prompts (e.g., extract → classify → route a support ticket).
  2. Pass the structured output of each step as input to the next.
  3. Compare quality vs. a single mega-prompt that tries to do all 3 at once.

4 Self-check

Q1You need reliable JSON output. Rank these by reliability: (a) ask for JSON in the prompt, (b) prefill with {, (c) use tool-use with a schema. Why?
Q2When does chain-of-thought hurt rather than help?
Q3You have a 3-step task. When do you chain 3 prompts vs. write one big prompt?
Q4Two few-shot examples vs. ten. What governs the right number?

3 Hands-on labs

Lab 4A — Build your own MCP server
~2.5 hours • Maps to scenarios: Dev Productivity, CI/CD
  1. Use FastMCP (Python) or @modelcontextprotocol/sdk (TypeScript).
  2. Expose 2 tools (e.g., git_status, run_tests), 1 resource (e.g., current diff), 1 prompt (e.g., "review-changes").
  3. Connect to Claude Desktop via stdio. Verify it appears in the tools list.
  4. Write deliberately bad tool descriptions; observe failures. Improve them; measure the gain.
  5. Bonus: switch to SSE transport and host on localhost.
Lab 4B — Write an Agent Skill
~1 hour
  1. Pick a recurring task (release notes, CSV cleanup, weekly report).
  2. Write SKILL.md with clear description and trigger phrases.
  3. Add supporting scripts/templates the skill references.
  4. Install and verify it triggers correctly from natural language — but not for unrelated requests.

3 Hands-on labs

Lab 5A — Add prompt caching to a previous lab
~1 hour
  1. Take your Lab 3A classification prompt. Add a long static system prompt (~2000 tokens of guidelines).
  2. Add a cache_control: {type: "ephemeral"} breakpoint at the end of the static portion.
  3. Make 5 calls in a row. Compare latency and reported token usage with/without caching.
Lab 5B — Reliability wrapper
~1.5 hours
  1. Wrap your Lab 1A agent in a retry layer: exponential backoff on 5xx errors, max-retries cap.
  2. Add tool-output validation: if a tool returns malformed JSON, retry the tool call with a clarifying message instead of passing garbage back to the model.
  3. Add a token-budget guardrail: terminate gracefully if the conversation exceeds a threshold.

Exam day playbook

1 24 hours before

Light review only — flashcards and your wrong-answer log. Do not learn new material. Confirm proctoring software works (system check). Charge your laptop. Clear your desk per proctoring rules.

2 During the exam

120 minutes for 60 questions = 2 minutes per question. Strategy:

Pass 1 (~75 min): answer everything you're confident on; flag the rest. Pass 2 (~30 min): work the flagged ones. Pass 3 (~15 min): final review. Don't leave anything blank — no penalty for guessing on multiple choice.

The wrong-answer trap: when two options both look defensible, ask "which is the minimum-footprint, most reliable choice for a production system?" That framing picks the right one most of the time.

3 Scenario priming

You'll get 4 of these 6 scenarios: customer support agent, code generation, research system, developer productivity, CI/CD pipeline, data extraction. Before reading questions in a scenario block, take 30 seconds to mentally identify the agentic pattern that fits (workflow vs. orchestrator-workers vs. evaluator-optimizer). That framing answers half the questions.

4 After

Scaled scoring rescales raw correct count to 100–1000. 720 to pass — roughly ~70–75% raw. You'll see pass/fail plus a domain-level breakdown, useful even if you pass.
